# SNMP Write (SET) Support Matrix — Cross-Vendor Comparison

Referenced from [`connectivity-methods.md`](../00-architecture/connectivity-methods.md) ("SNMP write coverage is inconsistent and often narrow... tracked per-vendor in each `mib-reference.md` and rolled up in `comparison/snmp-write-support-matrix.md`") and [`gui-cli-snmp-unification.md`](../00-architecture/gui-cli-snmp-unification.md) ("check the specific vendor's `mib-reference.md` and `comparison/snmp-write-support-matrix.md` first"). This file exists so SignalScope's per-device capability layer has one place to check "does an SNMP-SET fallback exist for this action on this vendor" instead of re-deriving it from seven separate `gui-cli-snmp-mapping.md` files.

**Reading this table**: ✅ = confirmed writable via a documented vendor or standard MIB path (a real SET workflow was found, not just a `MAX-ACCESS read-write` MIB declaration — several vendors define objects as read-write in the MIB source with no actual documented way to exercise that write, which is called out explicitly where it applies). ⚠️ = plausible/theoretical path exists (standard MIB object, or read-write MIB access) but **no confirmed working SET workflow** was found — treat as CLI-only until verified against a live device. ❌ = confirmed no path exists, or CLI-only by architectural necessity (e.g. an action that configures SNMP itself). — = not investigated this session.

Scope: the seven Tier 1-3 vendors. Appendix-tier vendors (D-Link, Fortinet) are summarized in their own `overview.md` GUI/CLI/SNMP mapping tables rather than here, since neither has an independently-confirmed SNMP-SET path beyond the standard baseline.

## Vendors with essentially no config-write surface (CLI-only in practice)

- **Arista EOS**: only 2 of 9 researched actions (`ifAdminStatus`, `ifAlias`) have any confirmed SNMP write path. Arista's own documentation states MIB support is read-only "unless otherwise noted."
- **Juniper Junos**: 0 of 8 switch-configuration actions researched have a confirmed SNMP write path; the only writable objects found are SNMP-agent self-configuration and generic system/RMON scalars. Combined with the candidate-config/commit model, Junos is functionally CLI/NETCONF-only for configuration in SignalScope's architecture.
- **MikroTik RouterOS**: RouterOS's own documentation states plainly that "SNMP write access is only available for selected OIDs" — confirmed writable objects are operational (`mtxrSystemReboot`, `mtxrUSBPowerReset`, `mtxrScriptRunCmd`) and system-identity scalars, not switch configuration. Directly grepped from the vendored `MIKROTIK-MIB.txt` (see `vendors/mikrotik/mib-reference.md`): these three are the **entire** read-write surface of the module — everything else, including the unusually rich `mtxrHealth`/`mtxrInterfaceStats`/`mtxrPOE` telemetry groups, is read-only.

## Vendors with a genuine, broader write surface

**Updated 2026-07-16 (Phase 2 verification pass)** — this section changed substantially from the original research pass:

- **HPE Aruba AOS-CX is now, by a clear margin, the vendor with the broadest confirmed SNMP write surface in this project** — confirmed write coverage across five distinct feature areas: interface physical-layer config (speed/duplex/autoneg), VLAN (creation, PVID, and trunk allowed-list — Extreme also has a version of this, see below, but Aruba's has cleaner egress-vs-ingress semantics), STP port-hardening (edge-port, BPDU Guard + timeout, Root Guard, Loop Guard), port security (fully read-write), and config persistence (checkpoint/save, RowStatus-driven). No other vendor in this project has confirmed write coverage in more than two of these areas.
- **Cisco IOS/IOS-XE** remains the second-broadest — a real VLAN-adjacent write path (access-VLAN assignment via `CISCO-VLAN-MEMBERSHIP-MIB`) and a real config-save RowStatus workflow (`CISCO-CONFIG-COPY-MIB`). This is not a coincidence with Aruba's config-save finding: both `CISCO-CONFIG-COPY-MIB` and `ARUBAWIRED-CONFIG-MIB` follow the same RowStatus create-row/poll/complete pattern described generically in [`standard-mibs.md`](../00-architecture/standard-mibs.md)'s Q-BRIDGE-MIB note — evidently a common enterprise-MIB design pattern worth SignalScope treating as a recognizable shape (a `ConfigurationCopy`-style RowStatus table) rather than a vendor-specific quirk.
- **Huawei VRP** gained one confirmed write path this pass (access-VLAN/PVID) — still far behind Aruba/Cisco, but no longer a zero-confirmed-writes vendor for VLAN specifically.
- **Extreme EXOS** moved from zero confirmed writes to two confirmed areas this pass (access-VLAN/PVID, and VLAN membership/creation with the egress-vs-ingress-conflation caveat noted above) — third-broadest by area count now, though each area is narrower than Aruba's or Cisco's equivalent.

## Dell SmartFabric OS10 (researched later, not yet in the grid above)

Dell OS10 was researched in a later pass (see `vendors/dell/`). **Updated Phase 2 (2026-07-22)**: no object is confirmed writable, but the evidentiary status changed materially — a first-hand read of Dell's complete OS10 User Guide MIB chapter confirmed **none of OS10's five enterprise MIBs is a configuration-action module** (no equivalent of Cisco's `CISCO-VLAN-MEMBERSHIP-MIB`/`CISCO-CONFIG-COPY-MIB` or Aruba's port-security/config/MSTP MIBs exists for this vendor at all — see `vendors/dell/mib-reference.md`). This rules out an entire category of write paths rather than leaving them unchecked, making Dell's row closer in kind to Arista/Juniper/MikroTik's **actively-confirmed-narrow** rows above than to a genuine research gap — the one remaining open question is narrower: whether the standard `Q-BRIDGE-MIB::dot1qPvid`/`IF-MIB::ifAdminStatus` objects (read-write per the base IETF MIB, same as every vendor) actually accept a SET on live OS10 hardware, which no documentation confirms or rules out and which would need a live device to resolve. Treat Dell as **CLI-only, verified-absence-of-enterprise-write-MIB** rather than "not yet researched to the same standard."

## Practical implication for SignalScope

Per the architectural rule in `gui-cli-snmp-unification.md` ("never assume an SNMP SET path exists... check the specific vendor's documented support first"): **the default assumption for any new GUI action on any vendor should be CLI-only**, with an SNMP-SET fallback offered only for the ✅ cells above. The ⚠️ cells are explicitly *not* safe to treat as working fallbacks — they represent "a MIB object exists that theoretically could do this," which several rows above (Cisco port-security being the clearest example) demonstrate is not the same as "this is a supported way to make the change."
